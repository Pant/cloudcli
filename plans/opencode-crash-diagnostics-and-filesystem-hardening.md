# OpenCode Crash Diagnostics and Filesystem Hardening

## CONTEXT

CloudCLI already centralizes OpenCode execution in the Providers runtime, sequences normalized events through the WebSocket run registry, and persists one generation-fenced current lifecycle record per canonical session. OpenCode stdout is parsed and forwarded, but stderr is only streamed to the live client; the runtime's `close` callback keeps the numeric code and discards the signal; subsequent generations replace the previous lifecycle row; and no persistent per-run process transcript or cgroup resource snapshot exists. The File Tree service catches recursive `readdir` failures and returns an empty subtree, but currently logs transient `ENOENT` races as errors. Runtime filesystem ownership such as `/home/dev/.local/state/opencode` belongs to deployment/bootstrap rather than the `cloudcli-src` application, so this plan makes CloudCLI tolerate and diagnose such conditions without attempting host/container ownership changes.

Backend implementation must follow `AGENTS.md` and `.agents/skills/backend-module-standards/SKILL.md`: feature behavior stays in owning modules, cross-module consumers use barrels, shared contracts live in `server/shared`, routes remain transport-only, and focused tests live under the owning feature. Validation is available through Node/tsx backend tests, backend typecheck, ESLint, and the server build.

## ANALYSIS

The core requirement is observability without changing the provider-neutral execution model. A provider runtime currently resolves `Promise<unknown>` and separately emits a normalized `complete` event. That split is sufficient for browser behavior but inadequate for durable diagnosis: lifecycle orchestration receives only generic success/failure, while the runtime has the actual stderr stream, OS signal, process timestamps, and process/cgroup context. The clean boundary is a structured provider runtime result returned when the process terminates, with optional fields for exit code, signal, diagnostic artifact path, stderr tail, and resource snapshot. OpenCode can populate the full result; other providers may return void and continue using their existing complete events.

Persistent output should use a per-run directory below a stable app data root, defaulting to `~/.cloudcli/logs/opencode`, and support an environment override for packaging/deployment. Each run needs a collision-safe name based on canonical app session/generation or a random run id, sanitized so session/project/prompt values cannot escape the directory. The transcript should preserve timestamped process metadata and raw stdout/stderr bytes as separate files or a clearly framed append-only log. Logging must be best-effort: permission/disk failures must never prevent OpenCode from launching or completing, and persisted metadata must never contain API keys, the full child environment, or prompt arguments. Retention should be bounded by configurable age/count/size so a long-running installation cannot accumulate logs indefinitely. The database should store only safe paths relative to the diagnostic root, bounded stderr tail text, and structured terminal/resource metadata.

Current `session_run_state` is intentionally one mutable row per session and later generations clear prior terminal fields. Preserving original crashes therefore requires a separate immutable history table keyed by `(session_id, generation)`, written only for current-generation terminal transitions and never rewritten by later runs. It should contain provider, timestamps, exit code, signal, terminal reason/message, diagnostic artifact reference, and sanitized resource JSON. A bounded cleanup policy can prune old history while retaining recent failures. The existing current-state row remains authoritative for recovery/status behavior; history is diagnostic evidence, not a recovery input.

On Linux, cgroup v2 files such as `/sys/fs/cgroup/memory.current`, `memory.peak`, `memory.events`, and `memory.stat` can provide useful container-level context. They cannot prove which child consumed memory and may be unavailable on macOS, Windows, cgroup v1, or restricted hosts, so collection must be injected/testable and fail open. Capturing process RSS just before close is unreliable after a crash; therefore resource snapshots should record available cgroup data at spawn and terminal time plus process timing, clearly labeling the scope as container/cgroup rather than child-only. Host core dumps and Docker event retention cannot be enabled from portable application code; CloudCLI can instead persist enough process metadata and provide explicit artifact locations for operators.

The normalized `complete` event may safely gain optional `signal` and concise diagnostic identifiers, but browser-facing payloads must not expose absolute server paths, cgroup internals, raw stderr, or provider-native ids. Durable lifecycle status can retain exit code and optionally signal, while detailed diagnostics stay server-side in SQLite/files. Exact-one-complete and manual-abort semantics must remain unchanged: aborted runs should not be misclassified as crashes, late old-generation callbacks must be fenced, and a logging failure must not create a duplicate terminal event.

The File Tree issue is separate and small: disappearing paths during recursive scans are normal time-of-check/time-of-use races. `ENOENT` should be treated like permission-denied cases for logging purposes—return `[]` without error-level noise—while tests retain logging for unexpected codes such as `EIO`. Metadata `lstat` failures are already intentionally ignored.

No external product decision blocks planning. Safe defaults can be configurable: diagnostics enabled by default, stable log root under `~/.cloudcli`, bounded stderr tail, bounded artifact retention, and fail-open resource collection. The implementation should document that deployment-specific ownership repair, core-dump enablement, Docker event collection, and container memory limits remain operator responsibilities outside this repository.

## PLAN

1. Introduce provider-neutral structured termination metadata and a best-effort OpenCode diagnostic artifact service that persists bounded stdout/stderr plus Linux cgroup snapshots without exposing prompts, secrets, or absolute paths to clients.
2. Add immutable per-generation diagnostic history to SQLite and integrate lifecycle orchestration so later runs cannot overwrite the original exit code, signal, resource context, or artifact reference.
3. Harden recursive File Tree scans by silently skipping disappearing entries while preserving error reporting for unexpected filesystem failures.
4. Run focused regression and production build validation, and document the remaining deployment-only actions that application code cannot perform.

## GUIDELINES

- Confine edits and commands to `/home/dev/code/cloudcli-src`; do not perform VCS operations or alter unrelated working-tree changes.
- Read and follow ./AGENTS.md and ./.agents/skills/backend-module-standards/SKILL.md for every backend item. Keep ownership in the Provider, Database, WebSocket, and File Tree modules; use module barrels for cross-module consumers.
- Preserve provider neutrality. OpenCode may return rich termination metadata, while other runtimes may continue returning no result; generic lifecycle code must handle both.
- Preserve exact-one-complete, manual-abort, detached replay, recovery, old-generation fencing, and current `session_run_state` semantics.
- Persist diagnostic files below a stable CloudCLI data directory, defaulting to `~/.cloudcli/logs/opencode`, with an environment override. Create directories lazily and fail open on filesystem errors.
- Never persist provider credentials, child environment values, command prompts, attachment contents, or full process arguments. Store only a safe command label/version, canonical app session/generation/run id, timestamps, stdout/stderr streams, and sanitized resource/termination metadata.
- Treat diagnostic artifact references stored in SQLite as paths relative to the configured diagnostic root. Never send absolute paths, raw stderr, resource files, or provider-native session IDs to browser clients.
- Bound stderr retained in SQLite independently from full diagnostic artifacts, using a tail limit that cannot make rows or websocket events unbounded.
- Keep diagnostic artifacts bounded by configurable retention. Cleanup must be best-effort, scoped strictly under the diagnostic root, and unable to delay or fail a provider run.
- Treat Linux cgroup measurements as container/cgroup context, not proof of per-child memory consumption. Support cgroup v2 when readable, return unavailable elsewhere, and never make execution depend on resource collection.
- Use append-only per-generation history for forensic evidence. Starting or completing later generations must not mutate a prior history record; stale-generation callbacks must not append a misleading terminal record.
- Keep `session_run_state` as the current actionable lifecycle source used by recovery/status. Historical diagnostics must not cause automatic recovery or change current-state precedence.
- The File Tree service should silently skip `ENOENT`, `EACCES`, and `EPERM` recursive-read failures, but continue logging genuinely unexpected errors such as `EIO`.
- Do not attempt to modify container ownership, Docker configuration, host core-dump policy, kernel journals, or memory limits from application code. Record these as deployment follow-ups in the final validation summary.
- Each item must add and run focused tests for its own behavior. Use `TSX_TSCONFIG_PATH=server/tsconfig.json node --import tsx --test ...` for backend alias-aware test files, then targeted lint/typecheck/build checks where practical.
