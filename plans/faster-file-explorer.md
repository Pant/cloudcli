# Faster File Explorer Opening

## CONTEXT

- `cloudcli-src` is a React 18 + TypeScript frontend with an Express + TypeScript backend. The frontend is built by Vite; backend and frontend type checking run through `npm run typecheck`. Backend tests use Node's test runner through `tsx`, while focused frontend tests can be invoked directly with `node --import tsx --test <test files>`.
- The Files tab lazy-loads the `FileTree` component only when `activeTab === 'files'` in `src/components/main-content/view/MainContent.tsx`. The component is unmounted whenever the user leaves the tab, so reopening the explorer creates a new `useFileTreeData` instance and starts another request.
- `src/components/file-tree/hooks/useFileTreeData.ts` currently blocks the entire explorer behind `FileTreeLoadingState` until `api.getFiles(projectId)` returns. It clears the tree on request failure and has no reusable project-level cache, stale-while-revalidate behavior, per-directory loading, or distinction between initial and background loading.
- `api.getFiles` calls `GET /api/file-tree/projects/:projectId/files`. The File Tree route currently accepts only `respectGitignore`; the service resolves the project and always calls `buildFileTree(projectRoot, 10, ...)`.
- `server/modules/file-tree/file-tree.service.ts` recursively walks up to ten directory levels before responding. It performs `readdir` for every traversed directory and `lstat` for every visible entry to populate size, modification time, permissions, and symlink metadata. A global configurable concurrency limiter bounds filesystem calls, but the response is still withheld until the complete traversal finishes.
- Generated and VCS directories are skipped through `IGNORED_DIRECTORY_NAMES`; optional `.gitignore` filtering is used by mentionable-file requests. System-critical paths are protected from recursion. Existing service tests cover sorting, ignored directories, gitignore behavior, traversal protection, and adapter-only mutation.
- The frontend tree recursively renders only directories included in `expandedDirs`, but all descendants have already been fetched. `children === undefined` is currently possible in the type and can be used to represent an unloaded directory; `children: []` can represent a loaded empty directory.
- Search (`useFileTreeSearch`) assumes the complete hierarchy is present and filters client-side. Folder ZIP download (`useFileTreeOperations`) recursively consumes `children`, so both features need an explicit complete-tree/subtree path if normal explorer browsing becomes lazy.
- Other consumers of `api.getFiles` (`useFileOpenResolver` and command-palette `useFilesSource`) require a complete recursive tree. `getMentionableFiles` also requires a complete tree with gitignore filtering. Existing default API behavior therefore needs to remain backward-compatible unless those consumers are changed deliberately.
- Backend changes under `server/` must follow `.agents/skills/backend-module-standards/SKILL.md`: keep route parsing thin, put filesystem behavior in the File Tree service, retain explicit injected dependencies, update shared contracts only when cross-file use requires it, add module-local tests, and run narrow tests plus practical build/typecheck/lint validation.

## ANALYSIS

The dominant cold-open delay is architectural rather than a React rendering issue: the explorer waits for a depth-10 recursive filesystem traversal and metadata lookup for every visible entry before it can show even the project root. Large repositories, network-mounted workspaces, broad project roots, or many small files amplify the delay. Merely changing the loading component or increasing filesystem concurrency would not remove the amount of work on the critical path and could worsen resource pressure.

The explorer should instead fetch only the immediate project-root entries first and render them as soon as one `readdir` plus the minimum necessary work completes. Directory contents should be requested when a user expands a directory. The API can support this without breaking complete-tree consumers by extending the existing list options with a validated target path, bounded depth, and metadata flag while preserving current defaults (`project root`, depth 10, metadata enabled). Explorer requests can use depth 0 and omit metadata on the critical path; detailed metadata can remain optional/defaulted and complete-tree consumers keep their current response shape.

Lazy loading introduces several correctness requirements. The frontend must distinguish unloaded directories from loaded empty directories, deduplicate concurrent expansion requests, reject stale results after project changes or refreshes, merge fetched children into the correct immutable tree node, and retain currently visible data during revalidation rather than flashing a full-screen loader. Explicit refreshes and file mutations must refresh the root plus directories that were already loaded so nested changes remain visible. A small project-keyed in-memory cache can make subsequent Files-tab openings immediate while a background refresh reconciles disk changes; it must be bounded and updated after successful loads.

Search and folder ZIP behavior cannot silently degrade to only the currently expanded portion. Search should request the complete project tree on demand before applying the existing client-side filter, and folder ZIP download should request the complete selected subtree before collecting files. These expensive traversals then occur only when the user invokes a feature that genuinely needs them, not on every explorer open. File resolver, command palette, and mention consumers should continue receiving the complete tree through the unchanged API defaults.

The backend must validate requested paths with the existing project containment logic, clamp depth to a conservative maximum, and parse transport values in the route. Metadata-free nodes can retain stable placeholder fields in the backend contract so existing consumers and UI types do not require a response union; later subtree/full-tree responses replace placeholders. Gitignore filtering must remain relative to the project root even when listing a nested target directory.

Performance acceptance should be observable structurally and through tests: a shallow metadata-free request reads only the requested directory, performs no `lstat`, and returns without visiting descendants; a nested request cannot escape the project root; default requests preserve recursive metadata behavior. Frontend tests should focus on extracted pure tree merge/cache/request-state utilities, because the repository has no established File Tree hook test harness. Integration validation should include backend File Tree tests, new focused frontend tests, typecheck, targeted lint, and client/server builds as practical.

No repository-external product decision blocks implementation. The conservative default is to preserve complete-tree API behavior for all existing non-explorer consumers, use lazy metadata-free requests only in the visual explorer, fetch complete data on demand for search and ZIP download, retain stale visible data while refreshing, and bound the in-memory cache to a small number of recent projects.

## PLAN

1. Extend the File Tree list contract so callers may request a project-contained target directory, a bounded recursion depth, and optional metadata while preserving the current complete recursive metadata response as the default. Prove shallow requests avoid descendant traversal and metadata work.
2. Add frontend API/query helpers and pure immutable tree/cache utilities needed for lazy directory loading, stale-request protection, and bounded project reuse.
3. Refactor File Explorer data flow and rendering around root-first loading: hydrate cached roots immediately, revalidate in the background, load children on expansion, expose per-directory progress, and refresh already-loaded branches after file operations.
4. Preserve full-tree-dependent features by loading complete data only when search or folder ZIP download is invoked, while leaving command-palette, file-reference resolution, and mention behavior backward-compatible.

## GUIDELINES

- Optimize time-to-first-files, not just spinner appearance. The normal File Explorer open path must not recursively walk the project or perform per-entry metadata calls before rendering root entries.
- Preserve the existing default `GET /api/file-tree/projects/:projectId/files` behavior for consumers that still require a complete tree. New route query parameters must be optional, validated in the route, and passed as typed service options.
- Resolve nested listing paths through the existing project containment boundary. Reject traversal or absolute paths outside the project before invoking `readdir`; keep gitignore matching relative to the project root.
- Clamp client-supplied depth to a documented small maximum rather than allowing unbounded traversal. Depth `0` means the requested directory's direct children only.
- Keep backend routes transport-only and filesystem orchestration in `file-tree.service.ts`. Continue using the injected filesystem adapter and concurrency limiter; do not import Node filesystem APIs into the service.
- Follow `.agents/skills/backend-module-standards/SKILL.md` for every touched backend file, including shared type documentation and File Tree module tests.
- Use `children === undefined` to mean a directory has not been loaded and `children: []` to mean it has been loaded and is empty. Do not infer loaded state from expansion alone.
- Deduplicate in-flight directory requests and guard every async result by project/generation so a project switch, refresh, or newer request cannot merge stale data.
- Cache only successful project trees, bound the cache to a small recent-project count, and revalidate cached content in the background. Cache failure or absence must fall back to ordinary network loading.
- Keep existing visible tree data during background refresh; use the full loading state only when there is no cached/current root to show. Show directory-local progress for lazy expansion.
- Refresh must reconcile the root and all currently loaded directories so create, rename, delete, and upload operations remain visible at nested levels. Avoid issuing duplicate requests for overlapping paths.
- Search must not pretend unloaded directories have no matches. On the first non-empty query, fetch a complete tree (respecting the explorer's normal ignore policy), then run the existing client-side filter; reuse that full snapshot until invalidated.
- Folder ZIP download must fetch a complete selected subtree before recursively reading file contents. A partially loaded UI node is not an authoritative folder manifest.
- Leave `useFileOpenResolver`, command-palette file sourcing, and mentionable-file behavior complete and backward-compatible unless an item's implementation requires a narrowly scoped call-site update.
- Prefer pure utility tests for immutable tree merging, loaded-path discovery, cache eviction, and request planning. Run focused tests first, followed by typecheck, targeted lint, and practical client/server builds.
