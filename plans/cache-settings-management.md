# Cache Settings Management

## CONTEXT

- The frontend is React 18 + TypeScript built with Vite. Settings is a modal rendered by `src/components/settings/view/Settings.tsx`, with desktop/mobile navigation in `SettingsSidebar.tsx`, tab typing in `types/types.ts`, initial-tab normalization in `hooks/useSettingsController.ts`, and command-palette metadata in `constants/constants.ts`.
- Settings tabs follow the reusable `SettingsSection`, `SettingsCard`, and `SettingsRow` composition. Shared controls come from `src/shared/view/ui`, including `Button` and the accessible controlled `Dialog` primitive suitable for a destructive confirmation modal.
- Settings strings use the `settings` i18n namespace. Ten locale files exist under `src/i18n/locales/*/settings.json`; English is the source language. Cache navigation and tab copy need locale keys, with safe English fallback text where translations are not available.
- Browser session history caching is already implemented in `src/stores/sessionMessageCache.ts` using IndexedDB database `cloudcli-session-message-cache`, with separate `messages` and `sessionMetadata` object stores. Records are keyed by authenticated user namespace and session. Both stores have `byUser` indexes; messages also have a `byUserSession` index.
- `SessionMessageCacheRepository` currently supports hydration, authoritative replacement, realtime upsert/delete, metadata operations, session enumeration, per-session removal, manifest cleanup, and persistence requests. It does not yet expose exact cache statistics or a clear-all operation.
- `src/stores/useSessionStore.ts` owns the application-scoped in-memory session store and wraps the repository for the current authenticated namespace. It exposes complete-session synchronization and coordinator-facing metadata/cleanup operations through `SessionStoreContext`, but it does not expose cache statistics, clear-all cache, or a user-triggered all-session force-sync operation.
- `src/stores/SessionMessageCacheCoordinator.tsx` and `src/stores/sessionMessageCacheCoordinator.ts` already fetch `/api/providers/sessions/manifest`, fetch complete histories for missing/changed/invalidated sessions, limit concurrency to three, clean entries absent from a valid manifest, and react to periodic/browser/websocket activity. The normal coordinator intentionally skips unchanged revisions, whereas the requested manual action says to fetch every session history.
- Complete history is fetched from `GET /api/providers/sessions/:sessionId/messages` by calling `sessionStore.synchronizeSession(sessionId, metadata)`. The manifest includes active and archived sessions and marks sessions without provider history as `historyReady: false`.
- Exact statistics should come from IndexedDB, not metadata totals: session count can be derived from the union represented by cached metadata/message records, and total cached messages can be counted efficiently through the message store's `byUser` index. Metadata `total` is not an exact stored-row count because realtime and metadata-only records can differ.
- Cache writes are serialized per session in `useSessionStore.ts`. A bulk destructive action must avoid racing queued writes or a simultaneous background reconciliation in a way that immediately recreates deleted data. Manual sync should reuse the manifest parser, complete-history synchronization, bounded concurrency, and metadata shape rather than creating a second incompatible sync policy.
- The focused repository tests are in `src/stores/sessionMessageCache.test.ts` and use Node's test runner with `fake-indexeddb`. Coordinator policy tests are in `src/stores/sessionMessageCacheCoordinator.test.ts`. The package-wide `npm test` script only includes backend tests, so frontend tests are run explicitly with `node --import tsx --test ...`. Integration checks include `npm run typecheck`, targeted ESLint, and `npm run build:client`.
- No backend changes are required: the authenticated manifest and full-history endpoints already provide the data needed by the requested feature.

## ANALYSIS

The feature has three user-visible parts that should share one cache-management boundary: a status summary, an explicit full synchronization action, and a destructive clear action. The Settings tab should not access IndexedDB directly. Repository operations belong in `SessionMessageCacheRepository`, current-user scoping and coordination belong in `useSessionStore`/the cache coordinator layer, and the tab should consume a small asynchronous API with loading, success, and failure states.

The manual sync action differs materially from the existing automatic reconcile. Automatic sync compares revisions and skips unchanged sessions to minimize traffic. “Fetch all sessions histories and sync them” should be implemented as an explicit force sync: fetch and strictly parse the authoritative manifest, preserve metadata-only rows for sessions whose histories are not ready, fetch complete histories for every history-ready active or archived session with bounded concurrency, then run authoritative cleanup. The UI should report completion or failure and refresh the statistics afterward. Individual session failures should be surfaced as a failed/partial operation rather than silently claiming all sessions are synchronized.

The clear operation should delete both cached message rows and cached session metadata in one user-scoped IndexedDB transaction, then refresh the displayed counts. This is more robust and efficient than looping through sessions. It should not clear unrelated `localStorage`, service-worker assets, preferences, credentials, or backend transcripts. The confirmation modal must state that only locally downloaded session history is removed and that server-backed histories can be downloaded again. Because the always-mounted background coordinator can repopulate data after clearing, the clear path needs coordination: either invalidate/suppress an overlapping reconcile and allow later normal activity to repopulate, or define a shared cache-operation controller that serializes manual sync/clear against coordinator runs. At minimum, the destructive operation must await queued cache writes and avoid claiming a persistent empty state if an in-flight sync is still writing.

The statistics display should show exact cached session and message-row counts for the same scope as the actions. It should load when the Cache tab mounts, refresh after synchronization and clearing, and expose loading/error states without breaking Settings if IndexedDB is unavailable. A zero-value result is valid and must be visually distinct from loading failure.

The user confirmed the cache scope is the currently authenticated account only. All statistics, synchronization, and deletion operations must use the current user namespace and preserve cached records belonging to other accounts that used the same browser. The UI must make this account-scoped behavior explicit.

The Settings tab registries are currently duplicated, and Voice already demonstrates drift between the sidebar, controller normalization, and command palette. Cache wiring must update every live registry consistently and should add focused normalization/registry coverage where practical. The UI should use existing design primitives, a destructive `Button`, and `Dialog` rather than `window.confirm`.

Key risks are concurrent background/manual synchronization, queued writes recreating data after clear, stale stats after external cache activity, incomplete force-sync reporting, IndexedDB failure/quota behavior, and accidental deletion beyond session history. The implementation should keep cache failure non-fatal, serialize management operations, use exact repository counts, preserve user namespace isolation unless explicitly directed otherwise, and validate repository behavior plus orchestration policy before typecheck/lint/build integration checks.

## PLAN

1. Extend the existing IndexedDB repository with exact current-user cache statistics and an atomic current-user clear operation. The repository remains the only layer that knows object-store/index details and must preserve every other user namespace.
2. Add coordinated cache-management operations above the repository. Expose statistics, a manual force-sync of every history-ready manifest session, and an account-scoped clear through the application cache/store context. Manual operations must serialize with the always-mounted background coordinator so a clear waits for in-flight synchronization and is not immediately undone by stale writes; force sync must fetch all histories regardless of unchanged revisions and report complete versus partial failure.
3. Add the Cache Settings tab and wire it into every live Settings registry. Display exact cached session/message counts, provide a “Sync all histories” action with progress/result feedback, and provide an account-scoped destructive clear action behind an accessible confirmation dialog. Refresh statistics after every operation and add localized Settings copy.
4. Optimize the user-triggered full-cache synchronization path for substantially faster completion while keeping automatic background synchronization conservative. Use a higher bounded concurrency for manual sync, eliminate revision/metadata work that force-all planning does not need, and avoid redundant full-transcript persistence where safely possible.

## GUIDELINES

- Scope every cache statistic, sync, and deletion to `getUserCacheNamespace(user)` as supplied by `SessionStoreProvider`. Never delete, count, or synchronize another browser user's namespace.
- “Clear cache” means the IndexedDB session-history cache only: both message rows and session metadata for the current account. Do not clear `localStorage`, `sessionStorage`, Cache Storage/service-worker assets, authentication state, preferences, credentials, backend transcripts, or other users' IndexedDB rows.
- Implement exact counts from IndexedDB indexes/records. Do not sum metadata `total` values as a substitute for stored message-row count.
- Make current-user clearing atomic across the `messages` and `sessionMetadata` stores. Use the existing `byUser` indexes and preserve fail-open behavior when IndexedDB is unavailable.
- Manual “Sync all histories” must strictly validate the manifest, include active and archived `historyReady` sessions, persist metadata-only entries for sessions not yet history-ready, fetch complete transcripts with bounded concurrency, and force every history-ready session to refresh even when its cached revision is unchanged.
- Coordinate manual sync/clear with automatic reconciliation. A clear must wait for already-running cache synchronization/writes, prevent stale pre-clear work from recreating rows afterward, and leave the account cache empty when the operation resolves. Normal later browsing or scheduled synchronization may cache histories again; explain this in the UI.
- Treat partial session-sync failures as an unsuccessful/partial result with useful counts. Do not show a blanket success message unless every eligible session completed.
- Cache functionality is optional. IndexedDB, quota, manifest, or history-fetch failures must not break chat or Settings; surface localized operation feedback and keep network chat behavior unchanged.
- Use existing frontend boundaries: IndexedDB logic in `sessionMessageCache.ts`, application/current-user orchestration in the store/coordinator layer, and presentation in the Settings tab. Do not add backend endpoints or duplicate the existing manifest/history contracts.
- Use `SettingsSection`, `SettingsCard`, `SettingsRow`, shared `Button`, and shared `Dialog`. The destructive confirmation must be keyboard accessible, use `variant="destructive"`, clearly name the current-account scope, and disable duplicate submissions while pending.
- Keep Settings tab metadata consistent across `SettingsMainTab`, `KNOWN_MAIN_TABS`, `SettingsSidebar`, `SETTINGS_MAIN_TABS`, `Settings.tsx`, and the legacy `SettingsMainTabs.tsx` if it remains in the repository.
- Add English source strings and corresponding keys to every registered settings locale. English fallback text is acceptable for locales where a reviewed translation is unavailable, but no tab should display raw i18n keys.
- Follow existing TypeScript/import/Tailwind conventions. No backend code or VCS operations are in scope.
- Run focused frontend Node tests explicitly because `npm test` targets backend files only. Finish each item with relevant tests, `npm run typecheck`, targeted ESLint, and `npm run build:client` where integration is touched.
- Keep automatic reconciliation at its existing conservative concurrency so periodic/background activity does not create excessive load. Performance tuning in this follow-up applies specifically to the explicit user-triggered “Sync all histories” operation.
- Manual synchronization must remain bounded rather than firing an unbounded request per session. Choose a materially higher concurrency with tests proving the manual and automatic limits are distinct, and preserve accurate partial-failure reporting and operation serialization.
