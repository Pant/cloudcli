# Nested OpenCode Sessions and Running Agents

## CONTEXT

- The requested behavior concerns CloudCLI's OpenCode integration. OpenCode persists every primary and subagent conversation as a row in its shared `opencode.db`; the native `session.parent_id` column is the structural relationship, and OpenCode's own Task tool creates recursive child sessions with `parentID` and allows configurable nested subagent depth.
- `server/modules/providers/list/opencode/opencode-session-synchronizer.provider.ts` currently indexes all active OpenCode session rows but deliberately ignores `parent_id`. It persists title, timestamps, project path, and agent through `sessionsDb.createSession`, so parent and child rows reach CloudCLI as unrelated flat sessions. The synchronizer probes optional OpenCode columns with `PRAGMA table_info(session)`, which is the compatibility pattern to retain for `parent_id` and any activity-query fields.
- CloudCLI's `sessions` table (`server/modules/database/schema.ts`) and `SessionRow` repository contract (`server/modules/database/repositories/sessions.db.ts`) have stable app-facing `session_id` values and separate provider-native `provider_session_id` values, but no parent relationship. A native OpenCode `parent_id` therefore cannot be treated as an app ID directly: app-created parent sessions can have a different canonical `session_id`, and child/parent rows can be discovered in either order.
- Database migrations are additive and run from `server/modules/database/migrations.ts`. Adding the existing OpenCode `agent` field resets `scan_state.last_scanned_at` so historical parent/subagent rows are re-indexed. The hierarchy migration should use the same rescan behavior.
- Initial and paginated project session payloads are produced by `server/modules/projects/services/projects-with-sessions-fetch.service.ts`. They currently expose flat, activity-sorted `SessionSummary` rows with `id`, provider, model, agent, title, and timestamp. `sessionsDb.getSessionsByProjectPathPage` paginates all rows flat, meaning a parent and descendants may cross page boundaries. The frontend currently uses loaded session count as the next offset.
- Session details, standalone archived-session payloads, and the running-session service live in `server/modules/providers/services/sessions.service.ts`. The two `session_upserted` producers are `server/modules/providers/services/sessions-watcher.service.ts` and `server/modules/websocket/services/chat-run-registry.service.ts`; both currently omit hierarchy metadata and must stay shape-compatible.
- The OpenCode database file is watched through `sessions-watcher.service.ts`. `OpenCodeSessionSynchronizer.synchronizeFile` currently queries only the newest session (`LIMIT 1`) and reports one ID, even though one shared SQLite write burst can create or update several parent/child sessions.
- CloudCLI's generic `chatRunRegistry` is the current source for `GET /api/providers/sessions/running`. It tracks one CloudCLI-started provider process per canonical app session ID. It counts the primary OpenCode session but cannot see native child sessions created inside that process.
- OpenCode's JSON run output does not provide CloudCLI a complete child lifecycle stream: the CLI filters output to the primary session and, in JSON mode, does not emit the Task tool's running transition. However, OpenCode persists Task tool state and child message/session rows in `opencode.db`. Running child discovery therefore needs a provider-owned, read-only database inspection that identifies active Task/subagent sessions and maps their provider IDs back to canonical app IDs. It must fail open for older/changed OpenCode schemas and must not replace `chatRunRegistry` as the generic source for primary CloudCLI runs.
- Frontend processing state is `SessionActivityMap` from `src/hooks/useSessionProtection.ts`. `src/components/app/AppContent.tsx` polls `/api/providers/sessions/running` every five seconds and synchronizes exact session IDs. `src/components/sidebar/hooks/useSidebarController.ts` derives the badge count from map size and constructs running mode only from sessions already loaded in each project's paginated session array, so a running child outside the loaded page can increase the badge while remaining absent from the running list.
- The active sidebar rendering chain is `SidebarProjectList` -> `SidebarProjectItem` -> `SidebarProjectSessions` -> `SidebarSessionItem`. `SidebarProjectSessions` currently maps a flat array. `SidebarSessionItem` owns desktop/mobile selection, running spinner, recent/attention indicators, rename, archive/delete, and provider-ID copy behavior.
- `src/components/sidebar/utils/utils.ts` is the existing pure normalization/sorting location. There are currently no focused sidebar hierarchy tests. Frontend tests use Node's built-in runner with `tsx` and are invoked explicitly; `npm test` only includes backend tests.
- Backend changes must follow `.agents/skills/backend-module-standards/SKILL.md`: keep routes transport-only, place behavior in owning services/repositories/providers, use module barrels for cross-module access, add tests in the owning module, and preserve stable app IDs at frontend boundaries.
- Repository validation commands are `npm run typecheck`, `npm run lint`, `npm run build`, and focused Node/tsx test commands. Work is confined to `/home/dev/code/cloudcli-src`.

## ANALYSIS

This is a data-model, realtime-status, derived-state, and interaction change rather than a visual-only indentation change. The reliable structural source is OpenCode's native `session.parent_id`; CloudCLI needs to retain the provider-native relationship, resolve it to canonical app IDs whenever possible, propagate it through every active-session payload, and build a recursive forest in the frontend. The forest must tolerate child-before-parent indexing, missing ancestors caused by pagination, malformed self/cyclic references, and arbitrary nesting depth.

The safest persistence model is to retain the provider-native parent ID on each CloudCLI row and derive/expose a canonical `parentSessionId` through repository resolution. Persisting only a canonical parent foreign key would lose information when a child is indexed before an app-created parent receives its provider ID. The native relationship should remain nullable and provider-scoped; unresolved children can temporarily render as roots and reparent automatically after later sync/upsert data resolves the parent. Assignment/duplicate-merge paths must preserve parent metadata.

Flat row pagination conflicts with complete recursive trees. The backend should paginate roots and return each selected root's loaded descendant closure, ordered deterministically within the subtree, while carrying explicit pagination metadata that does not use total returned node count as the next root offset. Root ordering should use the newest activity anywhere in the subtree so a newly active child brings its parent tree into the first page. The displayed project session total can continue to represent all session nodes, but pagination must separately track root progress/next offset. This prevents normal pages from splitting known trees and also makes active subagents likely to be hydrated with their ancestors.

Realtime updates need the same hierarchy fields as initial hydration. The OpenCode watcher should report every materially synchronized session from a shared DB update rather than only one newest row, within a bounded incremental strategy so it does not blindly rescan and broadcast every row on every write. Both websocket upsert producers must serialize parent metadata consistently. Frontend merges must preserve a known parent when a partial/older event omits it and must accept reparenting when authoritative metadata later resolves.

Running-child detection cannot be implemented solely in the generic run registry. The design should union generic registry runs with provider-owned OpenCode child activity discovered from `opencode.db`. The preferred evidence is persisted Task tool state (`pending`/`running`) with child-session metadata, supplemented only by carefully bounded child message-state inference if current schemas require it. The provider scanner must return active child provider IDs; the service maps those through indexed session rows, deduplicates them against registry entries, and returns canonical IDs plus enough session/project hierarchy metadata for the frontend to hydrate running rows that are not in its current page. Completion/removal from the authoritative five-second snapshot naturally decrements both the running list and total badge. Unknown schemas, locked/missing DBs, or malformed JSON must simply omit native child additions rather than break the endpoint.

On the frontend, a pure hierarchy builder should normalize parent IDs, create child lists, break cycles, sort roots by subtree activity and siblings by their own/subtree activity, and flatten only expanded branches with depth metadata. Expansion state belongs in the sidebar controller and is independent from project expansion. Parent rows with children should select normally and toggle their branch in the same click, satisfying the requested "clicking the parent folds/unfolds" while preserving the ability to open the parent conversation. Disclosure controls must stop propagation so keyboard/mouse users can toggle without accidental duplicate selection; selected descendants and branches containing running descendants should auto-expand. New child branches should default expanded so newly discovered subagents are visible, while explicit user collapses should remain respected.

Running mode should preserve ancestor context: include every active node, its ancestors, and (when loaded) active descendants, force open the paths needed to reveal running nodes, and count every distinct active primary/child session exactly once. A running snapshot enriched with project/session summaries should be merged into canonical project state before sidebar derivation, eliminating the current mismatch where the badge count exceeds visible running rows. Parent rows may show a descendant-running cue/count, but only exact active sessions should contribute entries to the authoritative processing map and total-agent count.

Normal project search is currently project-only. This task does not require redesigning conversation search, but running/project hierarchy filtering should not discard parent context when a matching or running descendant is retained. Archive hierarchy/cascade semantics are outside the requested active-sidebar behavior; relationship metadata should survive session details/archive serialization where inexpensive, but archive rendering and parent archive/delete cascades should remain unchanged unless required to keep types/contracts consistent.

The principal risks are app/provider ID races, tree pagination offsets, stale inferred OpenCode activity, watcher amplification, cyclic/orphan data, and desktop/mobile row interaction regressions. Focused backend tests should establish migration/repository mapping, recursive project pages, multi-row OpenCode sync, websocket payload shape, and active-child running snapshots. Focused frontend tests should establish forest construction, cycle/orphan behavior, expansion flattening, ancestor-preserving running derivation, enriched running snapshot merging, and static rendering/accessibility of nested rows.

No repository-external product decision blocks implementation. Conservative defaults are: active OpenCode sessions only; unlimited recursive depth in rendering with cycle protection; new branches expanded by default; a parent click both selects and toggles; running mode reveals required ancestor paths; all distinct active nodes count as running agents; and other providers retain their current flat/root-only behavior until they expose equivalent native child session rows.

## PLAN

1. Add a durable provider-parent relationship to CloudCLI sessions and teach the OpenCode synchronizer to capture recursive `session.parent_id` relationships reliably, including app/provider ID mapping races and multi-row updates from the shared OpenCode database.
2. Propagate canonical parent relationships through project/session hydration and realtime sidebar updates, and change project session pagination from flat rows to root pages with complete loaded descendant closures.
3. Extend the running-session service with OpenCode-native active Task/subagent discovery from `opencode.db`, union and deduplicate those child sessions with generic CloudCLI runs, and return enriched canonical session/project metadata so every running agent can be shown even when it was outside the loaded sidebar page.
4. Integrate hierarchy and enriched running snapshots into frontend canonical state, add pure recursive forest/flatten/filter derivation with defensive orphan/cycle handling, preserve ancestor context in running mode, and manage branch expansion state.
5. Render accessible recursive session rows in the desktop and mobile sidebar, with parent click folding/unfolding, visible nested depth/connectors, exact and descendant running indicators, automatic reveal of selected/running descendants, and preserved rename/delete/copy/session-selection behavior.

## GUIDELINES

- Confine every edit and command to `/home/dev/code/cloudcli-src`.
- Apply `.agents/skills/backend-module-standards/SKILL.md` to all work under `server/`: routes remain transport-only, behavior stays in the owning service/provider/repository, cross-module imports use barrels, tests live in the owning module, and shared backend definitions follow the repository's documented rules.
- Treat `session_id` as the only frontend-facing identity. OpenCode `session.parent_id` is provider-native and must be persisted/resolved behind the backend boundary; never emit raw provider parent IDs to the browser.
- Persist the native parent relationship even when its canonical parent row cannot yet be resolved. Child-before-parent discovery and app-created parent ID mapping must self-heal on later synchronization without duplicate rows.
- Preserve parent metadata through `assignProviderSessionId` duplicate merges and any upsert path. A partial event with no relationship field must not erase a known relationship; an authoritative changed relationship may reparent the row.
- Use OpenCode schema probing (`PRAGMA table_info`) and guarded JSON extraction so older or evolving OpenCode databases fail open. Missing, locked, malformed, or incompatible OpenCode data must not break project loading or `/sessions/running`.
- Do not infer child activity from recency alone. Count an OpenCode child as running only when current persisted Task/subagent tool state identifies it as pending/running (supporting known field-name variants), and remove it when the authoritative snapshot no longer reports it.
- Keep `chatRunRegistry` as the generic source of CloudCLI-started primary runs. Provider-owned OpenCode child discovery augments it; deduplicate by canonical app session ID and prefer the generic run's richer timing/interrupt metadata on collision.
- Native child runs are not independently abortable through the current gateway. Report them with `canInterrupt: false` unless implementation establishes a safe child-specific abort path; do not route parent abort controls to a child by accident.
- Project session pagination must be tree-safe: page root sessions, include the full active descendant closure for each returned root, sort roots by newest subtree activity, and expose an explicit next root offset/count so frontend pagination never uses returned node count as the next offset. Keep `sessionMeta.total` as the total active node count unless a clearly compatible contract is implemented and tested.
- Recursive tree construction must handle arbitrary supported depth, self-parenting, cycles, duplicate IDs, unresolved/missing parents, and a child whose reported parent belongs to another project. Never recurse indefinitely; malformed or unresolved nodes render as safe roots.
- Preserve current provider-neutral behavior. Claude, Cursor, and Codex sessions without structural parent metadata remain roots and should not regress.
- New branches default expanded so newly created subagents are visible. Record explicit user collapses so routine websocket upserts do not continually reopen them. Always reveal the selected session and running descendants, particularly in running mode.
- Clicking a parent session row both selects/opens that conversation and toggles its children. A dedicated disclosure control may also toggle with propagation stopped; it must be keyboard accessible and expose `aria-expanded`/descriptive labels.
- Only exact active session IDs count toward the running-agent badge. Ancestor rows included for context do not add duplicate counts, although they may display a descendant-running count/cue.
- Running-mode snapshots may hydrate sessions absent from the current project page. Merge them into canonical project state without corrupting root pagination offsets/totals or duplicating aliases.
- Keep archive/delete cascade semantics unchanged. Carry relationship metadata through session details/archive contracts when those touched serializers would otherwise lose it, but do not redesign archived sidebar nesting unless needed for contract consistency.
- Add user-visible sidebar copy to the sidebar i18n namespace with sensible English values and update parallel locale files when the established convention requires it; avoid hard-coded inaccessible labels.
- Prefer pure, testable hierarchy/running derivation helpers. Frontend tests are run explicitly with `node --import tsx --test ...`; `npm test` alone does not execute `src` tests.
- Each item runs its own focused tests plus practical typecheck/lint/build checks for its scope. Do not defer item validation to a final standalone verification TODO.
