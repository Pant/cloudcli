# Nested OpenCode Sessions Live Display Fix

## CONTEXT

- The prior plan, `plans/nested-opencode-sessions.md`, is complete on paper and its source changes are present in this working tree: OpenCode parent metadata, tree-safe project pagination, running-subagent discovery, hierarchy utilities, controller expansion state, and depth-aware sidebar rendering all exist.
- The active frontend rendering chain is the intended one: `AppContent` -> `Sidebar` -> `SidebarProjectList` -> `SidebarProjectItem` -> `SidebarProjectSessions` -> `SidebarSessionItem`. `SidebarProjectSessions` calls `buildSessionForest`, annotates it, flattens expanded branches, and passes depth/disclosure metadata to the row component. There is no alternate active flat sidebar implementation.
- The current client build contains the nested implementation. Both `/home/dev/code/cloudcli-src/dist` and the mounted `/opt/cloudcli-src/dist` contain `data-session-depth`, `parentSessionId`, and disclosure-label code. The source and `/opt/cloudcli-src` are the same mounted tree.
- The currently running CloudCLI backend is PID 7, launched through `/opt/cloudcli/node_modules/.bin/cloudcli`, whose executable resolves into `/opt/cloudcli-src/dist-server/server/modules/cli/cli.js`. It was started before the hierarchy work was loaded into the process.
- The live CloudCLI database at `/home/dev/.cloudcli/auth.db` has the pre-hierarchy `sessions` schema: it has `agent` but does not have `provider_parent_session_id`. This proves the active backend has not run the new migration and cannot return hierarchy metadata, so the browser necessarily receives a flat session list even though the current static client bundle can render trees.
- The actual OpenCode database at `/home/dev/.local/share/opencode/opencode.db` is suitable for hierarchy ingestion. Its live `session` table has `parent_id`; 89 active sessions were observed, 69 of them children. Sample child rows have existing parent rows and matching directories, including the sessions created for the prior nested-session plan. The provider source schema and data are therefore not the reason the current view is flat.
- On a restarted current backend, `runMigrations` would add `provider_parent_session_id` and reset `scan_state.last_scanned_at`, after which OpenCode synchronization should backfill the hierarchy. However, the migration reset is keyed only to adding/rebuilding the column. A partial deployment in which the column already exists but backfill never completed can remain flat indefinitely.
- The backend persists the provider-native parent relationship and exposes only canonical app IDs. `sessionsDb.getCanonicalParentSessionId` currently returns `null` for both a true root and an unresolved native parent. Initial hydration and both websocket upsert producers serialize that value directly.
- The frontend treats `parentSessionId: null` as an authoritative root and only preserves an existing relationship when the field is `undefined`. If a child is broadcast before its app-created parent receives the provider ID mapping, the child can be stored as a root. Mapping the parent later broadcasts only the parent; it does not rebroadcast children whose canonical relationship just became resolvable.
- `useProjectsState.ts` duplicates the page/upsert merge implementations exported and tested in `projectStateUtils.ts`. The live hook imports only `mergeRunningSnapshotsIntoProjects`, so focused utility tests do not fully exercise the code used by production websocket and pagination updates. There is already a concrete divergence in root-count handling for omitted parent fields.
- `/api/providers/sessions/running` enriches exact active rows but not the complete inactive ancestor closure. Frontend running derivation can preserve ancestors only if they are already loaded in the project. A running grandchild whose immediate parent is outside the loaded root page is therefore rendered as a safe root, which also resembles the old flat view.
- Existing component tests construct ideal canonical `parentSessionId` values directly. They prove the row renderer works, but they do not cover the real OpenCode SQLite -> CloudCLI database -> project/running payload -> live project state -> sidebar integration or child-before-parent mapping order.
- Backend work must follow `.agents/skills/backend-module-standards/SKILL.md`: keep transport routes thin, place behavior in owning repositories/services/providers, use feature barrels for cross-module access, add tests in the owning module, and document required exports.
- The working tree contains extensive unrelated in-progress changes. All implementation must preserve them and remain confined to `/home/dev/code/cloudcli-src`; version-control operations are out of scope.

## ANALYSIS

The immediate explanation for “the view is exactly as before” is established rather than speculative: the running backend is stale and its live database physically lacks the hierarchy column. The checked-in/currently built frontend cannot invent nesting without `parentSessionId`, so it correctly falls back to roots. A current backend restart is required to load the migration and backend serializers; rebuilding source alone cannot update code already loaded into PID 7.

The repair should not stop at an operational restart, because the audit exposed two real ordering/hydration defects that can reproduce a partially or fully flat view after restart. First, unresolved canonical parents are conflated with roots. This is especially likely for app-created parent sessions: OpenCode can persist a child before the runtime records the parent's provider ID. The child upsert then emits `null`, the frontend records it as a root, and no later child event is guaranteed when the mapping becomes resolvable. The contract needs three states without leaking native IDs: explicit root (`null`), resolved parent (canonical string), and unresolved/unknown relationship (field omitted or an explicit frontend-safe resolution state). Any event that makes a relationship newly resolvable must refresh affected descendants.

Second, running snapshots do not carry inactive ancestor context. Tree-safe normal pagination generally loads complete descendants for selected roots, but the running API intentionally hydrates off-page active sessions. If an inactive intermediate parent is absent, the hierarchy builder must detach the child defensively. The running contract should include the canonical ancestor closure as context rows while preserving the exact-active list/count and non-interruptible child semantics.

Migration/backfill also needs a durable one-time marker independent of column existence. The current migration handles the normal old-schema upgrade, including the live database observed here, but cannot distinguish “column exists and backfill completed” from “column exists because of a partial deployment.” A versioned marker can force one safe rescan for every installation at the new hierarchy compatibility level. The reset should remain idempotent and must not cause a full historical rescan on every startup.

Frontend state should have one tested merge implementation. Removing the private copies in `useProjectsState` will ensure page metadata, omitted unresolved parents, explicit roots, and later reparenting behave the same in tests and production. Focused hook/integration coverage should exercise actual event order, not only pure component props.

Validation must include the real OpenCode schema shape and a production-style migrated database. The safest live verification is to copy `/home/dev/.cloudcli/auth.db` and use the real OpenCode database read-only, run the current migration/synchronizer against the copy, and assert that the copied CloudCLI database and serialized project payload contain canonical root/child/grandchild edges. This avoids mutating the user's live database during tests. The final build must be produced, but replacing the already-running PID 7 is an operational restart outside source-file implementation; completion reporting must state clearly whether that process was restarted or still needs restart before the visible UI can change.

No product clarification is required. The intended behavior remains the prior plan's behavior: nested active OpenCode sessions at arbitrary depth with defensive cycle handling, new branches expanded by default, stable app-facing IDs only, and exact active sessions counted once.

## PLAN

1. Make hierarchy activation and backfill durable for existing installations by introducing an idempotent versioned rescan marker, and prove the current migration/synchronizer can convert a pre-hierarchy CloudCLI database plus real-shaped OpenCode rows into canonical nested payloads.
2. Make canonical parent resolution self-healing across child-before-parent and app/provider mapping races. Preserve the distinction between explicit roots and unresolved relationships at the browser boundary, and broadcast all rows whose canonical relationship becomes resolvable.
3. Consolidate production frontend project-state merging onto the tested helpers and add event-order integration coverage so unresolved events cannot flatten known children while explicit root/reparent events remain authoritative.
4. Include canonical inactive ancestor context in enriched running snapshots, merge it without altering exact active counts or pagination cursors, and verify off-page grandchildren render under their complete path.
5. Build and run an end-to-end production-style hierarchy smoke check, then document the required backend restart for the already-running stale process so the migrated backend and rebuilt assets are actually served.
