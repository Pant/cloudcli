# Browser Session Message Cache

## CONTEXT

- The frontend is React 18 + TypeScript and is built with Vite. Frontend logic lives under `src/`; frontend unit tests use Node's built-in test runner with `tsx` on individual `src/**/*.test.ts(x)` files. The repository-wide `npm test` script currently targets backend tests only, while `npm run typecheck`, `npm run lint`, and `npm run build:client` validate frontend integration.
- Authentication is provided by `src/components/auth/context/AuthContext.tsx`. A stable user cache namespace can be derived from `user.id` when present and otherwise `user.username`; platform mode exposes `platform-user`. Browser-persisted messages must be namespaced by this identity so one login cannot hydrate another login's conversations.
- `src/stores/useSessionStore.ts` is the current session-keyed in-memory source for the chat UI. It stores `serverMessages`, `realtimeMessages`, a reconciled `merged` view, fetch sequencing, status, and pagination metadata. It explicitly documents that messages are not browser-persisted. The hook is instantiated inside `ChatInterface`, so the store is currently scoped to that mounted chat component rather than the authenticated application lifetime.
- Persisted history is read from `GET /api/providers/sessions/:sessionId/messages`. Omitting `limit` requests the entire transcript; a numeric limit uses tail pagination. The backend provider contract and all provider readers already support `limit: null`, so loading complete history does not require changing provider adapters.
- `src/components/chat/hooks/useChatSessionState.ts` currently requests only the newest 20 normalized messages on ordinary session open, then uses `fetchMore` while scrolling upward. It has a separate explicit “load all” path and search navigation already requests `limit: null`. The UI independently limits initial DOM rendering to the newest 100 converted messages, which can remain as rendering windowing even when the entire normalized transcript is already present locally.
- `src/components/chat/hooks/useChatRealtimeHandlers.ts` routes normalized websocket events into the session store for active and non-active sessions. Optimistic user messages and most live normalized events use `appendRealtime`; streaming output uses a stable synthetic row and is finalized before the persisted transcript refresh. Completion refreshes the currently viewed session from the server.
- The websocket also emits `session_upserted` when a provider transcript changes on disk. `useProjectsState` currently refreshes only the viewed transcript in response and marks other sessions for attention. Reconnects are surfaced as a synthetic `websocket_reconnected` event.
- The project/sidebar API intentionally paginates sessions per project (20 by default, capped at 200 per request), so the frontend does not have an authoritative list of every session suitable for a complete background cache synchronizer. The database repository can enumerate session rows, but no existing provider route exposes a lightweight all-session sync manifest.
- Native IndexedDB is not currently used in the frontend and no IndexedDB wrapper dependency is installed. IndexedDB is the appropriate browser storage mechanism for large structured message payloads (including tool results and base64 image data), unlike synchronous and quota-constrained `localStorage`. A message-per-record schema avoids rewriting one huge session blob whenever a single message changes.
- Backend changes under `server/` must follow `.agents/skills/backend-module-standards/SKILL.md`: keep routes thin, put behavior in the owning provider service/repository, use module barrels for cross-module imports, add provider-module tests, and run narrow tests plus available build/typecheck/lint checks.

## ANALYSIS

The requested behavior has three connected outcomes: ordinary session opens must request complete history, cached history must hydrate from durable browser storage before the network returns, and the cache must stay warm for sessions the user is not currently viewing. Implementing only `limit: null` would satisfy complete history but make large sessions slower; implementing only IndexedDB would leave caches stale and incomplete. The design therefore needs a durable cache layer, an application-scoped store that can hydrate/write through that layer, and a background coordinator supplied with an authoritative session manifest.

IndexedDB should store normalized messages rather than rendered `ChatMessage` objects. Normalized messages are already the boundary shared by REST history, websocket events, reconciliation, and rendering, so caching them avoids duplicating transformation rules and allows future UI changes to reinterpret old cache data. Records should be scoped by authenticated user and session, distinguish server-backed and realtime rows, preserve deterministic ordering, and carry per-session metadata such as the backend revision last synchronized and fetch timestamps. Full server refreshes should atomically replace the server portion and the reconciled realtime portion; individual live inserts/stream updates should use targeted upserts. All cache operations must fail open: private browsing, denied IndexedDB access, quota exhaustion, malformed old records, or schema upgrades may disable persistence but must never break chat loading or sending.

The in-memory store should become application-scoped through a provider/context rather than being recreated inside `ChatInterface`. That gives the selected-session loader, websocket handlers, and global background coordinator one consistent slot map and one cache writer. On first access to a session, cached server/realtime rows should hydrate immediately and notify the active view; an authoritative full-history request should then refresh them. Fetch ticket ordering and existing optimistic/realtime reconciliation must be preserved so cache hydration or background sync cannot overwrite a newer response.

Ordinary session selection should request `limit: null` and mark backend pagination complete. The existing 100-message rendering window may remain to control React/DOM cost: “load all at once” applies to history retrieval and cache availability, not necessarily mounting every expensive markdown/tool component simultaneously. With full history resident, upward scrolling and “load earlier” can reveal already-local rows without further server pagination. Existing search and explicit load-all behavior should collapse onto the same all-history state rather than issuing redundant fetches.

For all-session synchronization, a lightweight authenticated backend manifest is preferable to repeatedly loading every project's paginated sidebar pages. A provider session route can return every indexed session's stable app id, provider, updated timestamp/revision, archive state, and whether provider history is available. The frontend coordinator can compare this revision against IndexedDB metadata, prioritize the currently selected or explicitly invalidated session, and fetch full history only for missing or changed sessions. Initial warm-up should use bounded concurrency to avoid flooding the server/browser, while “constant” synchronization should be hybrid rather than a tight poll: react immediately to `session_upserted`, successful completion, reconnect, browser focus/visibility/online events, and also perform a modest periodic manifest reconciliation. A periodic manifest also catches changes made by another browser/client or missed websocket events and permits cache cleanup for truly deleted sessions while retaining archived sessions listed by the manifest.

Realtime inserts should be written through to IndexedDB as they enter the session store. Stable message ids make the writes idempotent. Streaming should persist the accumulated synthetic row rather than every tiny delta, and finalization should replace that row. Completion/session-upsert invalidation then replaces transient cache state with the canonical complete transcript. If a global websocket cache listener is needed to cover periods where the chat view is unmounted, it must avoid duplicating in-memory ingestion; it can persist idempotent non-control message rows and schedule canonical session refreshes on terminal/update signals.

Important risks are large initial synchronization cost, IndexedDB transaction ordering, cache/user isolation, duplicated websocket rows, stale responses racing hydration/background refresh, and browser quota pressure. The implementation should bound background concurrency, serialize or version per-session cache mutations, reuse existing fetch tickets/reconciliation, use idempotent keys, request persistent browser storage when available, and expose graceful logging rather than user-facing failure for cache-only errors. Tests should cover schema/repository behavior with an IndexedDB test implementation, session replacement/upsert/order/user isolation, manifest route/service behavior, sync scheduling/revision comparisons, and the selected-session full-history request path.

No repository-external product decision blocks implementation. For the ambiguous edges, the plan adopts conservative defaults: cache both active and archived sessions returned by the server manifest, namespace rather than delete caches on logout/user switches, use bounded background concurrency, retain the existing 100-row DOM rendering window, and treat IndexedDB/cache failures as non-fatal.

## PLAN

1. Add a lightweight backend session cache manifest that exposes every indexed session's stable id and revision metadata without loading transcript contents. This gives the browser an authoritative, non-sidebar-paginated list for active and archived session synchronization.
2. Add a versioned IndexedDB repository for normalized session messages and sync metadata, with user scoping, atomic full-session replacement, idempotent realtime upserts, session removal, and fail-open behavior. Add a test-only IndexedDB implementation to exercise the real browser API contract under Node.
3. Refactor the session message store into an authenticated application-scoped provider and integrate cache hydration/write-through. Preserve fetch ordering and reconciliation, make message insertion idempotent, expose cache/sync metadata operations needed by the coordinator, and keep network history authoritative.
4. Add an application-level background synchronization coordinator. It will request storage persistence where supported, poll/reconcile the manifest on a modest interval, react immediately to websocket/focus/visibility/online signals, prioritize changed sessions, and fetch complete transcripts with bounded concurrency while skipping revisions already cached.
5. Change ordinary chat session loading to retrieve complete history by default, remove server-side message pagination from the normal scrolling path, and adapt the existing controls so older rows are revealed from the already-loaded local transcript rather than fetched in 20-row pages. Preserve the current limited DOM window and search/scroll behavior for performance.

## GUIDELINES

- Use IndexedDB, not `localStorage` or synchronous Web Storage, for normalized message content. Store messages as individual records keyed by user/session/source/message id and keep session sync metadata separately so incremental updates do not rewrite a huge blob.
- Namespace every cache read/write by the authenticated user identity (`id` when available, otherwise username). Never hydrate another user's records into the current store.
- Browser persistence is an optimization only. Any IndexedDB open, upgrade, transaction, parsing, quota, or persistence-request failure must degrade to the existing in-memory/network behavior without blocking chat.
- Complete REST history is canonical. Cached rows should render immediately, then be reconciled/replaced by an authoritative full transcript. Preserve `_fetchSeq`/`_appliedFetchSeq` protections and optimistic/realtime pruning so slower hydration/background requests cannot wind state backward.
- Make inserts/upserts idempotent by stable message id. Do not allow overlapping global and chat websocket listeners to create duplicate in-memory or cached rows.
- Do not persist control-only websocket frames as visible history (`complete`, `status`, permission events, subscription acknowledgements, progress events). Streaming cache writes must be throttled/coalesced through the store's stable synthetic stream row rather than one record per delta.
- Keep full transcript retrieval separate from full DOM rendering. The existing newest-100 rendering window may remain and reveal more cached rows locally as the user scrolls.
- Background sync must be bounded and event-assisted: use a small concurrency limit, prevent duplicate in-flight sync per session, react to `session_upserted`/completion/reconnect and browser activity, and use periodic manifest reconciliation as the eventual-consistency safety net. Do not tight-loop or fetch every unchanged transcript every interval.
- Cache manifest revisions must be deterministic from persisted session metadata and sufficient to detect transcript changes. Include archived sessions; remove only cache entries no longer present in a successfully fetched authoritative manifest for the same user.
- Backend work must follow `.agents/skills/backend-module-standards/SKILL.md`: thin provider routes, service/repository ownership, imports through module barrels, shared definitions only when genuinely cross-module, provider-module tests, and documented public exports.
- Do not change provider history adapters or their `limit: null` semantics unless validation proves a provider violates the existing shared contract.
- Follow existing TypeScript/import/style conventions. Keep unrelated pagination for sidebar session lists intact; this task changes conversation-message loading, not project/sidebar session pagination.
- Validation should be narrow first, then integration checks. Frontend Node tests may be run explicitly with `node --import tsx --test <files>` because the package `test` script only includes backend patterns.
